# Melly open-source review

Produce an evidence-backed, report-only review of the `melly` Git repository. If the user names a crate, module, change, or contribution, focus there and inspect its public dependencies and documentation. Otherwise review the repository as a whole. This skill is not a request to edit code, install tools, publish packages, contact maintainers, or change another repository.

Read this repository's `AGENTS.md`, `README.md`, `docs/workspace.md`, `docs/architecture.md`, `docs/development.md`, and relevant source before judging a boundary. Preserve the distinction between implemented behavior, scaffolds, design drafts, and future promises. Inspect `git status` and the relevant diff so findings are attributed to the correct state and existing user changes remain untouched.

## Review lenses

1. **Module naming and interpretability.** For each relevant crate/module, compare its name with actual responsibilities, exports, dependency direction, and nearby documentation. Ask whether a new contributor can predict where to find or add behavior. Flag misleading, overlapping, or overbroad names only with a concrete navigation or API consequence. Respect established project and crate branding; a subjective naming preference alone is not a finding.
2. **Applicable standards and contracts.** Identify the specific Rust/Cargo, XDG/Unix-socket, Wayland, web, accessibility, or other normative contract that applies to implemented behavior. Check observable code and tests against the correct version and required clauses using primary official specifications or documentation when verification is needed. State the standard, version, evidence, and limitation. Do not claim general “standards compliance” from formatting or a successful build. Do not mark unimplemented behavior noncompliant; mark it not yet assessable and identify the future validation needed. Keep Melly-specific design requirements separate from external standards.
3. **Tests and independent-contribution decisions.** Map public behavior, policy/security boundaries, error and fallback paths, compatibility promises, and adapter contracts to assertions and executable tests. Run focused existing checks when safe; start with `cargo fmt --all --check`, targeted `cargo test -p <package> --locked`, and targeted Clippy or feature checks. Avoid a full Servo/all-features build merely to populate the report. Do not use an arbitrary line-coverage percentage as a pass threshold. If coverage instrumentation exists, report its number and limitations; otherwise state coverage qualitatively. Decide whether an outside contribution in the reviewed area can be accepted or rejected from repeatable tests and written contracts, or whether manual/private judgment remains essential.
4. **README and documentation freshness.** Verify important README claims and quick-start commands against current manifests, source, tests, features, paths, and status. Check relevant crate READMEs and architecture/development docs where they serve as contributor entry points. Cite the exact claim and contradictory or supporting artifact. A clear draft/future statement is not stale simply because it is not implemented; an implemented claim without implementation is stale.
5. **Other open-source quality and commit hygiene.** Check proportionately for discoverable contribution instructions, reproducible build/test commands, license and third-party attribution, dependency and release/version hygiene, public API compatibility, security and permission boundaries, reviewable issue/diagnostic paths, portability, and useful CI or manual validation. Inspect tracked, staged, and untracked files before judging what could be committed. Main repository files must not contain credentials, real tokens/keys, or developer- or machine-specific environment configuration. Local-only configuration and scratch material may live under the gitignored `.dev/` directory; verify the ignore rule and that none of its files are already tracked. Flag example, trial, and test-try files outside `.dev/` when they do not serve the maintained test suite, runnable product, or contributor-facing documentation. Do not print credential values in the review; report paths and redacted evidence only. Report missing items as release or contribution risks only when the project's current maturity makes them necessary. Do not assume a code of conduct, changelog, crates.io publication, or a particular governance model is mandatory for an early scaffold.

## Evidence and verdict

For each finding, give severity, affected scope, source path and line or command output, concrete consequence for contributors/users, and a specific verification or improvement. Separate observed defects from design risks and unimplemented areas. Mark checks not run and why; never imply a test passed if it was not run. If a claim depends on a changing standard, cite the primary source and say when it was checked.

Lead the report with an **independent-contribution readiness** verdict for the requested scope: `ready`, `conditional`, or `not ready`. `Ready` requires a usable contract, repeatable tests for the material behavior, and no unresolved high-impact issue in that scope. `Conditional` means narrow contributions can be evaluated but named gaps require manual review. `Not ready` means the relevant behavior or contract cannot yet be independently evaluated. Explain the verdict with evidence, not a numerical score.

Then cover all five lenses even when a lens has no finding. Prioritize actionable findings; include a short “not assessed” section and the exact checks performed. If the user asks for fixes after reading the report, treat that as a separate implementation request.
